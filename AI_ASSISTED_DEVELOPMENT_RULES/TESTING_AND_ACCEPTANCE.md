# 测试与验收规则

## 1. 基本原则
测试是完成条件，不是可选项。自动化测试、真实浏览器测试、真实设备测试、第三方服务测试和生产验收属于不同证据层级，不能互相冒充。测试命令必须从仓库实际脚本、配置和 CI 中确认；没有执行就不能报告通过。

## 2. 每轮验证顺序
按项目实际能力和风险执行：
1. 格式检查与静态分析。
2. 类型检查。
3. 与本次修改直接相关的单元测试。
4. 集成测试和关键流程测试。
5. 全量回归测试。
6. 构建、打包及产物完整性检查。
7. 安全检查、依赖检查和敏感信息扫描。
8. 可行时执行浏览器自动化或端到端测试。
9. 必要时进行真实环境实际使用测试。

记录执行日期、代码提交 SHA、运行环境、实际命令、通过／失败数量、失败日志或 CI 链接、跳过项及原因。性能数据必须记录环境、样本和基准；没有测量数据时只描述预期改善。

## 3. 最低测试矩阵
按功能适用性覆盖以下场景，不机械测试不存在的功能：

| 类别 | 至少检查的内容 |
|---|---|
| 正常流程 | 有效输入、预期输出、成功反馈 |
| 空值与缺省 | 空内容、缺失字段、首次使用 |
| 非法输入 | 错误格式、超长输入、越界值、恶意格式 |
| 边界条件 | 最小／最大值、空列表、单条与大量数据 |
| 重复操作 | 连续点击、重复提交、重试和幂等性 |
| 失败恢复 | 请求失败、异常、取消、重试、部分成功 |
| 持久化 | 保存后刷新、关闭再打开、重启后恢复 |
| 并发与一致性 | 并行请求、重复写入、跨标签页冲突、并发修改 |
| 网络状态 | 断网、慢网、超时、迟到响应、连接恢复 |
| 权限 | 未登录、无权限、越权请求、权限变化 |
| 历史回归 | 原有功能、旧数据格式、已修复缺陷 |
| 界面与可访问性 | 常见视口、移动布局、键盘操作、焦点、提示和错误恢复 |
| 构建交付 | 可重复构建、打包内容正确、敏感文件未进入制品 |

核心流程至少有一组可复现成功案例和一组可复现失败案例。涉及浏览器扩展时，模拟 DOM 测试不能替代真实目标网站验证；涉及第三方 API 时，模拟服务测试不能证明真实账号、权限、限流和服务行为均正确。

## 4. 失败处理
测试失败后：
1. 读取完整失败信息，定位失败阶段。
2. 判断是产品缺陷、测试缺陷、环境问题还是第三方故障。
3. 尽可能建立可复现案例和回归测试。
4. 进行最小修复。
5. 重跑失败项及相关回归测试；按风险重跑全量测试和构建。
6. 在报告中保留失败原因、修复提交和最终结果。

禁止删除失败测试、放宽断言、跳过失败、修改 CI 规则来制造通过结果。环境问题导致测试不能执行时，应标记“未执行”，说明原因和替代证据，不可标记为通过。

## 5. 必须主动提醒用户进行实际使用测试的条件
GPT 应优先自行执行全部可自动化的检查，不把人工测试当作默认工作。出现下列任一情况，且现有工具无法充分覆盖时，必须在适当时机主动提醒用户进行实际使用测试：
- 结果依赖真实浏览器、设备、操作系统或扩展权限。
- 结果依赖真实第三方账号、登录态、权限、服务限流或线上数据。
- 自动化测试无法可靠模拟用户操作、页面动态变化、输入法、下载、通知或系统交互。
- 涉及真实数据迁移、用户数据保留、备份恢复或版本升级。
- 关键流程的正确性、安全性或发布资格必须由目标环境确认。
- 重大视觉或可用性问题只有在实际设备或目标页面才能确认。

提醒必须包含：
1. **原因：** 哪个风险无法通过现有自动化测试排除。
2. **目标：** 具体要验证的功能和场景。
3. **步骤：** 清晰、有限、可直接执行的操作；必要时说明在哪里打开、点击什么。
4. **预期结果：** 明确的成功信号。
5. **失败记录：** 应记录的错误、页面状态、时间、版本或截图；避免要求上传密钥和私人数据。
6. **后续处理：** 用户反馈失败后，GPT 应基于新证据继续定位和修复。

不得只写“请测试一下”，也不得在自动化已充分覆盖且没有现实环境依赖时要求用户重复测试。用户不需要掌握命令行或编程知识才能完成被要求的实际使用测试。

## 6. 验收状态
- **自动化通过：** 已执行的自动化检查均通过；不代表真实环境已验收。
- **待验收：** 自动化检查通过，但必要的实际使用测试或其他验收证据尚未取得。
- **待修复：** 存在失败、阻断问题或未解决的 P0／阻断性 P1。
- **允许合并：** 所有必须需求、自动化检查、安全与数据审查、回退方案均满足，且必要验收证据齐全；仍需用户授权执行合并。
- **发布已验证：** 只有在获得授权、实际部署完成并检查关键流程后才能使用此状态。

## 7. PR 验收清单
- [ ] PR 对应最新且明确的提交，文件变更范围已核对。
- [ ] 必须需求逐项对应实现与证据。
- [ ] 回归测试可以发现原缺陷。
- [ ] 相关测试、全量测试和构建结果真实且可追溯。
- [ ] 最新提交的 CI 没有失败、取消或未解释的跳过项。
- [ ] 安全、权限、数据兼容、备份与回滚已检查。
- [ ] 需要的真实环境测试已完成；未完成的项目明确标记且不冒充通过。
- [ ] 变更、风险、提交 SHA、测试命令、结果与回退方法已记录。
- [ ] 当前状态明确标记为“开发中／待修复／待验收／允许合并”。

任一必须条件未满足时，不得判定“允许合并”。CI 全绿不能替代需求核对、安全审查或必要的实际使用验收。
