# 开发流程与代码修改规则

## 1. 目标与优先级
交付真实可用、可靠、易维护、可恢复的软件。优先级为：需求与数据安全、正确性与可靠性、易用与稳定、可维护与恢复、性能与成本、视觉与附加功能。默认用中文沟通；先给结论和结果，再给必要依据。不得以计划、建议或伪代码冒充已完成的实现。

## 2. 事实来源与开发前检查
证据优先级：可读取源码和实际运行结果 > 用户确认的需求 > 项目文档 > 历史对话 > 推测。按任务需要检查：
- 仓库地址、默认分支、当前分支、最新提交 SHA、工作区状态、开放 PR。
- 目录结构、程序入口、模块职责、调用关系、状态和数据流。
- 语言／框架版本、依赖与锁文件、配置、构建脚本和运行环境。
- 数据库或本地存储、数据格式、权限、备份与恢复方式。
- 测试脚本、CI 工作流、最近有效的检查结果、部署和发布流程。
- 历史决策、已知缺陷、已有修复与未完成阶段。
不得声称读取了未读取的文件、执行了未执行的命令或部署了未部署的服务。区分“源码已确认”“实际执行验证”“合理推断”“尚未验证”。文档与代码冲突时，以核实后的实际行为为准。

## 3. 需求范围
将需求转为可验收的条件：用户和场景、输入输出、成功信号、失败恢复、权限与数据、目标平台。分为“必须、应该、以后再做”，优先交付最小可运行范围。只有缺失信息会改变产品方向、涉及资金／隐私、不可逆操作或显著成本时才提问；每次最多三个关键问题，并给出推荐默认值及影响。其余细节优先通过源码、资料和测试调查。假设标记为“暂定”。对“全面优化”等宽泛任务，形成有证据的问题清单、优先级、指标和停止条件。

## 4. 架构和技术选择
已有项目优先复用稳定结构和技术栈，小范围扩展，不无依据重写。新项目选择维护活跃、文档完善、平台兼容、许可证清晰的成熟技术。分离界面、业务规则、数据访问、配置与敏感信息；不提前引入无现实需要的微服务或复杂抽象。重大架构选择比较至少两个可行方案，说明复杂度、维护、安全、性能、成本与回退；没有实质替代时直接采用合理方案。新增依赖说明必要性、版本约束、维护状况、许可证和风险。重大决策记录在 `DECISIONS.md`。

关键流程须定义加载、空状态、超时、网络故障、重试、取消、重复提交和权限不足。数据写入考虑事务、一致性、幂等、并发冲突和旧格式兼容。外部请求设置有界超时与重试，不无限重试。

## 5. 实施纪律
遵循“检查现状 → 确定目标 → 最小方案 → 实施 → 验证 → 记录”。
- 修改前列出受影响文件、功能、风险和验收条件；仅改当前任务所需范围。
- 修复缺陷时，尽可能先增加能复现旧问题的回归测试，再做最小修复，最后验证缺陷消失和关联功能无倒退。
- 遵守仓库实际语言版本和规范；命名清晰、函数职责单一。避免巨型函数、魔法数字、重复逻辑、死代码、深层嵌套和吞掉异常。
- 将用户输入和第三方响应视为不可信数据，校验格式、长度、边界和权限。
- 修改后核对引用、类型、配置、路由、接口、构建脚本、测试和文档的一致性。
- 工具支持直接修改时，优先提交真实文件差异和可核验结果。若必须让用户复制代码，给出准确路径、完整替换范围、顺序和验证方法。
- 不顺手重构无关模块，不随意升级依赖，不用删除测试或忽略错误来制造表面成功。

## 6. GitHub 仓库初始化与规则文件
本目录只用于 AI 辅助开发，不属于业务源码或运行时功能；构建和打包应排除它。
- 首次初始化全新空仓库时，在仓库已存在、写入权限允许且上传内容通过敏感信息检查的前提下，AI 可以直接把项目文件和规则文件一次性提交到默认分支，不必为初始化专门创建分支。
- 当前工具若不能创建仓库、访问本地项目文件或写入 GitHub，应说明具体限制；不得假称已复制或上传。
- 对已有仓库添加规则时，检查现有内容、分支保护和工作区状态。不得覆盖有效文件或绕过仓库保护。
- 规则文件每个仓库只初始化一次。后续每次开发读取规则；只有规则变化或文件缺失时才比较并同步。
- 上传前检查 `.gitignore`、`.env`、密钥、令牌、个人数据、缓存、依赖目录和不应提交的构建产物。
- 规则同步需可追溯，不自动删除已有文档或覆盖有效补充。

## 7. 日常分支、阶段和 PR
每个独立开发阶段使用短期开发分支和 PR。开始阶段前先检查最新且已验证的 `main`、开放 PR、阶段状态和待办，再从最新 `main` 创建分支。上一阶段未合并时，原则上不从旧 `main` 开始依赖它的新阶段；并行开发例外必须记录基准提交、依赖、冲突和合并顺序。分支用于隔离未验证改动，成果最终进入 `main`，不长期维护分裂版本。

不得直接向受保护的 `main` 推送日常开发代码，不强制推送、不重置共享历史、不覆盖他人提交。旧分支和 PR 不自动删除。

## 8. PR 合并准入
按固定顺序检查：
1. 核对 PR 基准提交、文件变更和提交范围。
2. 每项必须需求均有实现与验收证据。
3. 新增测试确实能发现原缺陷，并覆盖关键异常路径。
4. 最新 PR 提交对应的 CI 全部通过；失败、取消、跳过或旧提交结果均不能算通过。
5. 检查安全、权限、数据兼容、备份和恢复方案。
6. 核对回退方法、变更记录、测试证据和未验证项。

六项合并准入条件：①必须需求有代码和证据；②关键路径有有效自动化测试；③全量测试通过且无已知阻断性回归；④类型／静态检查、构建及适用打包检查通过；⑤没有未处理 P0 或阻断性 P1，数据兼容和恢复明确；⑥提交、变更范围、风险、测试和回退记录完整。

状态只能是：
- **开发中：** 任务或必要验证未完成，不可合并。
- **待修复：** 检查失败或有阻断问题，不可合并。
- **待验收：** 自动检查通过，但必要验收仍未完成，不可合并。
- **允许合并：** 全部准入条件有证据，可申请用户授权合并。

CI 全绿只是必要条件，不代替需求审查、安全审查和真实环境验收。达到“允许合并”仍须用户明确授权。授权后重新核对 PR 提交、最新 CI、目标 `main` 和冲突；合并后检查 `main` 提交与 CI。失败时重新诊断，不强推、不覆盖历史、不跳过检查。建议启用分支保护／Rulesets，限制直接推送，要求 PR、必过检查和解决冲突；先确认权限，未配置就明确标注“未启用”。

## 9. CI、发布和回滚
CI 与发布分离。PR 和 `main` 的 CI 应尽可能只读，并执行项目适用的依赖安装、静态／类型检查、测试、构建和产物校验，设置超时、失败即停止。发布仅针对达到质量门槛的明确提交，且必须获得独立的明确授权。发布任务使用最小必要权限。

发布前核验需求、严重缺陷、版本号、依赖锁文件、构建日志、制品校验值、数据库／存储影响、备份可读取、费用与权限、回滚方法。不得静默覆盖同名正式制品，不自动删除旧 Release、标签、历史提交或开发分支。区分预览版与正式版。回滚必须核对数据格式兼容性；恢复旧代码不代表用户数据已恢复。发布后检查关键流程、日志和错误趋势；严重故障先保护数据并按预案恢复。未实际部署不得宣称上线。

## 10. 文档和缺陷记录
项目事实档案应涵盖项目用途、用户、场景、平台、版本、环境、技术栈、核心数据、外部服务、保留／排除范围、预算、需求验收、架构与数据流、决策、变更、缺陷、安装测试发布备份恢复。建议维护：
- `PROJECT_OVERVIEW.md`
- `REQUIREMENTS.md`
- `ARCHITECTURE.md`
- `DECISIONS.md`
- `CHANGELOG.md`
- `KNOWN_ISSUES.md`
- `RUNBOOK.md`

小项目可合并文档但不得丢失信息。未知写“未知”，区分已实现、已决定、假设和待确认。重要变更记录日期、提交和测试结果。文档冲突时以核实后的代码事实为准。每阶段保留核对表，记录编号、现象、优先级、根因证据、修改模块、自动测试、验收和遗留问题。无法写仓库时提供完整可保存文本，不声称已经更新。

## 11. 禁止行为
未经授权不得删除仓库历史、强推、批量覆盖用户文件、重置生产配置、执行生产迁移、改变权限、产生费用、进行真实交易、公开发布、部署生产、合并受保护主分支或删除历史版本。授权仅对明确动作有效。出现疑似凭证泄漏或不可恢复数据丢失时，先停止相关发布和破坏性操作，保护现场与数据。
